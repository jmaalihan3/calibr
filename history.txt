### Design Decisions

#### Decision 1: SPA Architecture (vs Server-Side Rendering)
**Chosen**: Single-Page Application with REST API

**Pros:**
- Clean separation of frontend and backend
- Smooth user experience without page refreshes
- Easy to add mobile app or other clients later
- Modern, scalable architecture
- Backend API is independently testable
- Follows current web development best practices

**Cons:**
- More JavaScript complexity (state management in client)
- Two separate codebases to maintain
- CORS configuration needed
- All JavaScript must load before app is interactive
- More moving parts to debug

**Alternative**: Server-Side Rendered Multi-Page Application
- Would be simpler initially (single process, less JavaScript)
- Better for SEO (not relevant for this use case)
- Traditional request-response model
- Page refreshes on every interaction (worse UX)
- Harder to add mobile app later

**Rationale**: Despite higher initial complexity, SPA provides better UX and future extensibility. For an exam-taking application, avoiding page refreshes is crucial for maintaining user focus and flow.

#### Decision 2: Client-Side State Management
**Chosen**: JavaScript object in memory

**Pros:**
- Simplest implementation
- No server-side session management needed
- Stateless backend API
- Easier to scale horizontally

**Cons:**
- State lost on page refresh
- No persistence across browser sessions
- User can't pause and resume exam

**Alternative**: Server-side sessions or localStorage
- Server sessions would require session management, cookies, complexity
- localStorage would persist across refreshes but adds complexity

**Rationale**: For a prototype with 5-question exams (takes ~2 minutes), page refresh is unlikely. Adds complexity that hasn't been requested yet. Can add localStorage later if needed.

#### Decision 3: SQLite Database
**Chosen**: In-process SQLite database

**Pros:**
- Zero configuration - file-based
- Perfect for local development and testing
- No separate database server needed
- Sufficient for prototype requirements
- Easy to reset (just delete file)

**Cons:**
- Not suitable for production/concurrent users
- File locking issues with multiple writers
- No built-in replication or backup

**Alternative**: PostgreSQL or MySQL
- Would require separate server installation
- Overkill for local testing prototype
- Same Python code would work with minimal changes

**Rationale**: Project requirements specify "run and test locally for now." SQLite is ideal for this. Production deployment would need PostgreSQL, but migration is straightforward (just change connection string).

#### Decision 4: Vanilla JavaScript (No Framework)
**Chosen**: Plain JavaScript (ES6+)

**Pros:**
- No build step or bundler needed
- Simpler development setup
- Matches tech stack requirements (HTML, CSS, JS)
- Lower learning curve
- Faster initial development for small app
- No framework lock-in

**Cons:**
- More boilerplate for state management
- Manual DOM manipulation
- No component reusability
- Would become unwieldy for larger apps

**Alternative**: React, Vue, or Svelte
- Would provide better state management
- Component-based architecture
- Requires build tooling (webpack, Vite)
- Steeper learning curve

**Rationale**: For a 3-screen app with minimal complexity, vanilla JavaScript is sufficient and avoids unnecessary tooling. If requirements expand to admin panels, dashboards, or complex interactions, should reconsider using a framework.

#### Decision 5: Three-Layer Architecture
**Chosen**: Database → Services → API Router

**Pros:**
- Clear separation of concerns
- Easy to test each layer independently
- Business logic isolated from HTTP concerns
- Database implementation can change without affecting API
- Follows clean architecture principles

**Cons:**
- More files and abstractions than needed for simple app
- Some functions are thin wrappers

**Alternative**: Single-file monolith or two-layer (DB + API)
- Would be simpler for tiny app
- Harder to test and maintain as app grows

**Rationale**: Even for prototypes, good architecture pays off quickly. Clear layers make testing easier (all tests pass!), debugging clearer, and future changes safer.

### Design Decisions

#### Decision 1: Database Schema - Add Columns vs Separate Table
**Chosen**: Add `unit` and `unit_name` columns directly to questions table

**Pros:**
- Simpler queries (no JOIN needed)
- Better performance for typical queries (get questions with unit info)
- Easy to filter by unit with WHERE clause
- Intuitive data structure (unit info lives with question)

**Cons:**
- Denormalized (unit_name repeated for each question in same unit)
- ~40 extra bytes per question (minimal: 20 questions × 40 bytes = 800 bytes)
- If unit names change, need to update multiple rows

**Alternative**: Separate units table with foreign key
- Would be more normalized (unit info in one place)
- More complex queries (always need JOIN)
- Overkill for 4 static units

**Rationale**: For this use case with only 4 units and 20 questions, denormalization is acceptable. Query simplicity and performance outweigh normalization benefits. Unit names are stable academic standards unlikely to change.

#### Decision 2: Results Grouping - Client-Side vs Server-Side
**Chosen**: Client-side grouping in JavaScript

**Pros:**
- Keeps API simple and generic
- Flexible presentation without API changes
- Reduces server processing
- Better separation of concerns (API returns data, UI handles presentation)

**Cons:**
- More JavaScript code complexity
- Client must do grouping work
- Could be harder to cache grouped results

**Alternative**: Server-side grouping with dedicated endpoint
- Could create `/api/exams/{id}/results/by-unit` endpoint
- Would return pre-grouped data structure
- Less client-side logic

**Rationale**: With only 5 questions per exam, client-side grouping is trivial. Keeping API simple and presentation-agnostic is better long-term design. Future features (different groupings, filtering) can be implemented client-side without API changes.

#### Decision 3: Unit Display in Results - Separate Tables vs Single Table
**Chosen**: Separate table for each unit

**Pros:**
- Clear visual separation between topics
- Easy to scan specific unit performance
- Natural grouping matches mental model (units as distinct topics)
- Per-unit scores immediately visible
- Scales well if units have many questions

**Cons:**
- More DOM elements (more tables)
- Slightly more complex to render
- Can't easily sort across all questions

**Alternative**: Single table with unit column
- Simpler to implement (one table render)
- Easy to sort by any column
- But loses visual unit separation

**Rationale**: Educational context demands clear topic separation. Students need to identify strengths/weaknesses by unit. Visual grouping matches how courses are structured. Single-table view would make it harder to see "I got 2/2 on Unit 3 but 0/2 on Unit 12."

#### Decision 4: Question Numbering in Grouped Results
**Chosen**: Preserve original exam order numbering (1-5)

**Pros:**
- Consistent with exam-taking experience
- Easy to reference ("I got question 3 wrong")
- Matches student's mental model

**Cons:**
- Numbers not sequential within each unit (e.g., Unit 8 might have questions 2 and 5)
- Could be confusing without context

**Alternative**: Renumber within each unit (1, 2, 3...)
- Sequential within groups
- But loses connection to exam order

**Rationale**: During exam review, students think "I wasn't sure about question 3" not "I wasn't sure about the second Unit 12 question." Preserving exam order numbering maintains continuity between exam-taking and review.
